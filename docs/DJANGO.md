# Django: установка и сопровождение

## Решение

04.11.2026 пользователь выбрал Django после замечания техлида к самописной CMS. Используется Django 5.2 LTS со встроенной Django Admin. Пользователи, группы, права, сессии, CSRF и формы работают средствами Django. Ограничение входа — django-axes, контроль параллельных изменений — django-concurrency. Версии зафиксированы в `requirements.txt`.

Вёрстка и контракт чтения `/api/articles?language=en`, `/api/articles/{slug}` сохранены. Старые setup/login/session API и самописный редактор удалены из активного комплекта. Исходный код прежней CMS сохранён только в локальной рабочей папке, вне GitHub.

## Локальный запуск

Нужен Python 3.11+. `START-SITE.cmd` готовит окружение, зависимости, миграции и предлагает создать администратора. Ручная установка описана в README. Новое хранилище `data/django/` независимо от `data/cms/` и `data/demo/`.

Подготовка без сервера и создания пользователя:

```text
python scripts/start_django.py --prepare-only
```

Создание администратора и запуск:

```text
.venv\Scripts\python manage.py createsuperuser
.venv\Scripts\python manage.py runserver 127.0.0.1:8345
```

Пароль задаёт владелец, скрыто, минимум 12 символов. Если порт занят, выберите другой. Не запускайте старый и новый сервер на одном порту. `python scripts/serve_cms.py --port 8345` теперь тоже запускает Django. Прежняя веб-форма создания первого аккаунта больше не используется.

## Доступ редакторов

Суперпользователь создаёт пользователей через «Пользователи». Для редактора включите «Активный» и «Статус персонала», выдайте просмотр, добавление и изменение статей и изображений галереи — шесть прав. Удобно объединить эти права в группу «Редакторы». Статус суперпользователя и управление пользователями редактору не нужны. Все редакторы с этими правами работают с общими статьями.

Смена пароля через стандартный интерфейс или команду:

```text
.venv\Scripts\python manage.py changepassword ЛОГИН
```

Прежние сессии после смены пароля перестают проходить проверку. Сессия действует до восьми часов и завершается при закрытии браузера, если он не восстанавливает session cookies. Для аварийного снятия блокировки входа используется `manage.py axes_reset_ip АДРЕС`. Блокировка после десяти неудачных попыток действует одну минуту для непосредственного IP соединения.

За прокси все клиенты по умолчанию могут иметь общий IP. Перед внешним запуском настройте доверенные прокси в django-axes и проверьте разделение клиентов. Произвольному X-Forwarded-For приложение не доверяет.

## Перенос прежних статей

Остановите старую CMS. Сохраните приватную копию всего `data/cms/` либо `data/demo/`. Выберите один источник, не смешивая рабочие и пробные материалы. Сначала примените миграции Django.

```text
.venv\Scripts\python manage.py import_legacy_cms --source data/cms
```

Без `--apply` выполняется проверка без записи контента. Для переноса:

```text
.venv\Scripts\python manage.py import_legacy_cms --source data/cms --apply
```

Сохраняются идентификаторы, адреса, тексты, даты, обложки и порядок галереи. Прежние RU-публикации становятся черновиками согласно правилу публичного английского сайта. Исходная SQLite открывается только для чтения. Аккаунты, пароли и сессии не переносятся — пользователей Django нужно создать заново. Повторный импорт существующей статьи отменяется без перезаписи.

При отсутствующем или повреждённом изображении перенос отменяется. При ошибке записи новые записи откатываются, новые файлы удаляются; существующие файлы не заменяются. Сначала проверьте импорт на копии. В ходе подготовки кода реальные рабочие базы не переносились.

## Данные и резервные копии

В `data/django/` находятся `db.sqlite3`, `uploads/` и локальный `.secret-key`. Для отдельного хранилища задайте `DJANGO_DATA_DIR` с абсолютным путём вне `site/`. Не помещайте базы, сессии, загрузки и секреты в публичную папку или GitHub.

Перед резервным копированием остановите Django и скопируйте весь `data/django/`, включая возможные SQLite-файлы журнала. Для восстановления остановите сервер, верните весь комплект и запустите ту же версию кода. На внешнем сервере отдельно сохраняется секрет окружения. Восстановление сначала проверяется локально. Неиспользуемые картинки автоматически не удаляются: это сохраняет файлы при откате и конфликте.

## Внешний запуск — отдельный этап

GitHub Pages не запускает Django. Нужны сервер Python, постоянное приватное хранилище, HTTPS, резервные копии и процесс WSGI. `runserver` — для разработки. В зависимости включён Waitress:

```text
.venv\Scripts\python -m waitress --listen=127.0.0.1:8350 irsite.wsgi:application
```

Перед запуском задайте окружение:

| Переменная | Значение |
|---|---|
| `DJANGO_ENV` | `production` |
| `DJANGO_SECRET_KEY` | Приватный случайный ключ от 50 символов, вне Git |
| `DJANGO_ALLOWED_HOSTS` | Точные согласованные хосты через запятую, без `*` |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | Точные HTTPS origins, если нужны схеме размещения |
| `DJANGO_DATA_DIR` | Постоянный приватный каталог |
| `DJANGO_TRUST_HTTPS_PROXY` | `1` только за настроенным доверенным HTTPS-прокси |

В production требуются ключ и хосты, отключён DEBUG, включены Secure cookies, перенаправление на HTTPS и HSTS. Прямой внешний доступ к WSGI должен быть закрыт. При `DJANGO_TRUST_HTTPS_PROXY=1` прокси обязан удалять входной X-Forwarded-Proto и выставлять собственный. Настройки IP для django-axes зависят от схемы размещения и проверяются до внешнего доступа.

Выполните `manage.py migrate`, `manage.py collectstatic --noinput`, `manage.py check --deploy`. Прокси обслуживает `/static/` из `data/django/static/`, `/assets/` и `/documents/` — из соответствующих папок `site/`. Остальные запросы передаются Django. Не открывайте весь `site/` как запасной маршрут: `/admin/` должен попадать в Django. **`/uploads/` всегда проходит через Django**, чтобы картинки черновиков оставались закрытыми. Нельзя раздавать весь `data/` или MEDIA_ROOT напрямую.

HSTS для всех поддоменов и включение в preload-список не активированы: они требуют отдельного решения владельца домена. Соответствующие предупреждения `check --deploy` оцениваются перед размещением.

Canonical и sitemap пока содержат действующий адрес GitHub Pages. При согласованном переезде их нужно обновить и повторить SEO-проверку. Покупка домена, DNS, почта и внешняя публикация в текущую подготовку не входят.
